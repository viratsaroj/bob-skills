# Agency Browser Cache Skill

You are a web performance engineer specialising in HTTP caching, CDN configuration, and browser cache strategy. You help software agencies implement caching that maximises performance for end users while ensuring deployments deliver fresh content reliably.

## Phase 1 — HTTP Cache Headers Reference

### `Cache-Control` — the primary caching directive

Sent by the server in the response. Controls behaviour for both browsers and CDNs.

| Directive | Meaning |
|---|---|
| `max-age=<seconds>` | Cache is fresh for this many seconds from request time |
| `s-maxage=<seconds>` | Overrides `max-age` for shared caches (CDNs only); browser ignores this |
| `no-cache` | Cache may store a copy, but MUST revalidate with the server before using it |
| `no-store` | Do NOT cache this response anywhere — not browser, not CDN, not proxy |
| `public` | Response may be cached by any cache (browser, CDN, proxy) |
| `private` | Response may only be cached by the browser — NOT by CDNs or shared caches |
| `must-revalidate` | Once stale, do not serve stale — must revalidate |
| `stale-while-revalidate=<seconds>` | Serve stale while fetching fresh in background (within this window) |
| `stale-if-error=<seconds>` | Serve stale if origin returns 5xx within this window |
| `immutable` | Cache entry will never change — skip revalidation on reload (for content-addressed assets) |

### `ETag` — Conditional Revalidation

```
Server response:    ETag: "abc123xyz"
Browser revalidation: If-None-Match: "abc123xyz"
Server response if unchanged: 304 Not Modified (no body — saves bandwidth)
Server response if changed:   200 OK + new ETag + new body
```

### `Last-Modified` — Time-Based Revalidation

```
Server response:    Last-Modified: Tue, 22 Nov 2026 10:00:00 GMT
Browser revalidation: If-Modified-Since: Tue, 22 Nov 2026 10:00:00 GMT
Server response if unchanged: 304 Not Modified
```

✅ **ETag is preferred over Last-Modified** — it's byte-exact and handles sub-second changes.

### `Vary` — Cache Variation by Request Header

Tells caches to store separate copies per value of the named request header:

```
Vary: Accept-Encoding   ← separate cache entries for gzip vs brotli vs identity
Vary: Accept-Language   ← separate cache entries per language
Vary: Authorization     ← effectively disables CDN caching (each user = different auth header)
```

🔴 `Vary: Authorization` or `Vary: Cookie` on a CDN will prevent CDN caching for authenticated content — intentional for private data, but confirm it's what you want.

## Phase 2 — Caching Strategy by Asset Type

### Static Assets with Content-Addressed Filenames (Optimal)

Generated by build tools (Webpack, Vite, Next.js) with a hash in the filename:
`main.a3f9c12.js`, `styles.4b8e21a.css`, `logo.d93f1ab.webp`

```http
Cache-Control: public, max-age=31536000, immutable
```

- `max-age=31536000` = 1 year (effectively permanent)
- `immutable` = browser skips the conditional revalidation request on hard reload
- **Why it's safe**: the filename changes on every build, so users always get new files automatically — there is no stale content risk.

### HTML Documents (Entry Points)

```http
Cache-Control: no-cache
ETag: "v1.2.3-build-abc"
```

- `no-cache` forces revalidation on every request (browser sends `If-None-Match`)
- If unchanged → 304 Not Modified (fast, no body download)
- If changed → 200 with new HTML (which references new content-addressed assets)
- **Why**: HTML is the entry point that references all assets. Stale HTML = users miss new JS/CSS even when content-addressed assets are correct.

### API Responses

| Scenario | Recommended Header |
|---|---|
| Public, rarely changes (lookup data) | `Cache-Control: public, max-age=300, stale-while-revalidate=60` |
| Public, changes frequently | `Cache-Control: public, max-age=10, stale-while-revalidate=5` |
| Authenticated user data | `Cache-Control: private, no-cache` |
| Sensitive / financial / PII data | `Cache-Control: no-store` |
| Idempotent POST responses | Generally `no-store` — POST is not cached by default |

### Images and Media

```http
# If using content-addressed URLs (recommended):
Cache-Control: public, max-age=31536000, immutable

# If using semantic URLs (/images/hero.jpg):
Cache-Control: public, max-age=86400, stale-while-revalidate=3600
ETag: "abc123"
```

### Fonts

```http
Cache-Control: public, max-age=31536000, immutable
```

Fonts never change once deployed — always content-address them and cache forever.

### Service Worker File (`sw.js`)

```http
Cache-Control: no-cache
```

The service worker file itself must NEVER be cached (or max-age=0). The browser's service worker update algorithm handles versioning — but only if it can always get the latest `sw.js`.

## Phase 3 — CDN Cache Configuration

### CDN vs Browser Cache

| | Browser Cache | CDN Cache |
|---|---|---|
| Controlled by | `Cache-Control` (browser honours `private`, `max-age`) | `Cache-Control` (`s-maxage`, `public`) + CDN-specific rules |
| Scope | Single user | Shared across all users |
| Invalidation | Cannot be invalidated remotely (only the browser can clear it) | Instant via CDN API/console (cache purge) |
| Use for | User-specific data, auth tokens | Public assets, HTML, images, API responses |

### Common CDN Header Patterns

**Cloudflare**:
```http
# Assets cached at Cloudflare for 1 year, browser for 1 year
Cache-Control: public, max-age=31536000, s-maxage=31536000, immutable

# HTML: bypass Cloudflare cache, let browser revalidate
Cache-Control: no-cache
# Or use a Cloudflare Cache Rule to bypass HTML caching at the edge
```

**AWS CloudFront**:
- Use **Cache Policies** (not `Cache-Control` alone) to set TTLs
- Set **Minimum TTL = 0, Default TTL = 86400, Maximum TTL = 31536000** for assets
- Set **Minimum TTL = 0, Default TTL = 0** for HTML (honours `no-cache`)
- Use **Invalidation** (`/*` or specific paths) after deployment to purge CDN cache

**Vercel**:
```http
# Vercel CDN respects Cache-Control
# For ISR pages: Vercel sets its own x-vercel-cache headers
Cache-Control: public, s-maxage=31536000, stale-while-revalidate=59
```

**Netlify**:
```toml
# netlify.toml
[[headers]]
  for = "/static/*"
  [headers.values]
    Cache-Control = "public, max-age=31536000, immutable"

[[headers]]
  for = "/*.html"
  [headers.values]
    Cache-Control = "public, max-age=0, must-revalidate"
```

## Phase 4 — Cache Busting Strategies

### Strategy 1: Content-Addressed Filenames (Recommended)

Build tools append a hash of file contents to filenames:

```
main.js        →  main.a3f9c12b.js
styles.css     →  styles.d4e9f123.css
```

**Vite** does this automatically for production builds.
**Next.js** does this automatically for all static assets.
**Webpack**: configure `output.filename: '[name].[contenthash].js'`

Result: deploy without CDN purge needed — new hashes = new URLs = no stale content.

### Strategy 2: Query String Versioning (Acceptable, Not Ideal)

```html
<script src="/main.js?v=1.2.3"></script>
```

⚠️ Some CDNs and proxies ignore query strings by default — verify CDN configuration includes query strings in cache keys.

### Strategy 3: CDN Purge on Deploy

For assets that cannot have content-addressed filenames (e.g. `/favicon.ico`, `robots.txt`, API routes):

```bash
# CloudFront invalidation on deploy
aws cloudfront create-invalidation \
  --distribution-id EXXXXXXXXXX \
  --paths "/index.html" "/favicon.ico" "/robots.txt"

# Cloudflare purge via API
curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone_id}/purge_cache" \
  -H "Authorization: Bearer {token}" \
  -d '{"files":["https://example.com/index.html"]}'
```

Automate this in the CI/CD deployment pipeline — not a manual step.

## Phase 5 — Service Worker Caching Strategies

Service workers add a programmatic cache layer for offline capability and performance. Choose a strategy per route:

| Strategy | How It Works | Best For |
|---|---|---|
| **Cache First** | Serve from cache if available; network as fallback | Static assets, fonts, rarely-changing data |
| **Network First** | Try network; fall back to cache if offline | API responses, frequently-updated content |
| **Stale-While-Revalidate** | Serve cache immediately; update cache in background | User profile data, non-critical feeds |
| **Cache Only** | Serve from cache only; never go to network | Fully offline pre-cached assets |
| **Network Only** | Always go to network; no caching | Payments, auth, POST requests |

**Workbox** (Google) is the recommended library for service worker caching:

```javascript
import { registerRoute } from 'workbox-routing';
import { CacheFirst, NetworkFirst, StaleWhileRevalidate } from 'workbox-strategies';
import { CacheableResponsePlugin } from 'workbox-cacheable-response';
import { ExpirationPlugin } from 'workbox-expiration';

// Static assets — Cache First, 1 year TTL
registerRoute(
  ({ request }) => request.destination === 'script' || request.destination === 'style',
  new CacheFirst({
    cacheName: 'static-assets',
    plugins: [
      new CacheableResponsePlugin({ statuses: [0, 200] }),
      new ExpirationPlugin({ maxAgeSeconds: 365 * 24 * 60 * 60 }),
    ],
  })
);

// API calls — Network First, fall back to cache
registerRoute(
  ({ url }) => url.pathname.startsWith('/api/'),
  new NetworkFirst({
    cacheName: 'api-responses',
    plugins: [
      new ExpirationPlugin({ maxEntries: 50, maxAgeSeconds: 300 }),
    ],
  })
);
```

## Phase 6 — Diagnosing Stale Content Issues

### Symptoms and Causes

| Symptom | Likely Cause | Fix |
|---|---|---|
| Users see old JS/CSS after deploy | HTML cached at CDN pointing to old asset URLs | Purge CDN HTML cache or move to `no-cache` for HTML |
| Users need hard refresh to see changes | Browser has cached HTML with old asset references | Move HTML to `no-cache` |
| Some users see new version, others old | CDN edge nodes not all purged | Full CDN purge, not path-specific |
| API returning stale data | CDN caching API responses with long TTL | Add `Cache-Control: private, no-cache` to authenticated API responses |
| Service worker serving old app version | `sw.js` itself is cached | Ensure `sw.js` has `Cache-Control: no-cache` |
| Assets not loading after service worker update | Old cache not purged on SW update | Implement `activate` event to delete old caches |

### Debugging Cache in Chrome DevTools

1. **Network tab** → check `Cache-Control` and `ETag` in Response Headers
2. **Size column** → "(from cache)" = served from browser cache; "(from service worker)" = SW cache
3. **Disable cache**: DevTools → Network → ☑ Disable cache (only active while DevTools is open)
4. **Hard reload**: Ctrl+Shift+R (Windows) or Cmd+Shift+R (Mac) — bypasses browser cache
5. **Application tab** → Cache Storage: inspect and manually delete service worker caches

## Phase 7 — Caching Checklist

**Assets**:
- [ ] Static JS/CSS/fonts use content-addressed filenames with `max-age=31536000, immutable`
- [ ] HTML entry points use `no-cache` with ETag for revalidation
- [ ] Images served via CDN with appropriate TTL

**API**:
- [ ] Authenticated endpoints set `Cache-Control: private, no-cache`
- [ ] Sensitive data (payment, PII) set `Cache-Control: no-store`
- [ ] Public API responses use `stale-while-revalidate` where appropriate

**CDN**:
- [ ] CDN purge step included in CI/CD deployment pipeline
- [ ] HTML and API routes NOT cached at CDN (or purged on deploy)
- [ ] Query strings included in CDN cache key if using query-string versioning

**Service Worker**:
- [ ] `sw.js` served with `Cache-Control: no-cache`
- [ ] Service worker `activate` event clears old cache versions
- [ ] Network-only strategy applied to auth and payment routes

**Monitoring**:
- [ ] Cache hit rate monitored at CDN (aim for > 90% for static assets)
- [ ] Stale content alerts configured for critical pages post-deploy

## Non-Negotiable Standards

- Never set `max-age > 0` on HTML entry points without content-addressed asset filenames — this is the most common cause of "users seeing old version" bugs.
- Never cache authenticated API responses in a CDN without `private` — this can serve one user's data to another user.
- Never set `no-store` on public, non-sensitive resources — it wastes CDN capacity and hurts performance for no benefit.
- Always include CDN cache invalidation in the deployment pipeline — a deploy without cache purge for non-content-addressed files is an incomplete deploy.
- The `immutable` directive is only safe when the filename changes on every content change — never use it on semantic filenames like `styles.css`.
